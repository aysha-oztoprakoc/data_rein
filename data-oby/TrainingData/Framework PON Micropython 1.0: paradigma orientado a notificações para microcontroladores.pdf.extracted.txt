RESUMO

O Paradigma Orientado a Notificações (PON) surge como uma solução inovadora
para superar limitações recorrentes em paradigmas de programação tradicionais,
como redundância de código e alto acoplamento. A concretização dos conceitos do
PON tem sido realizada por meio de frameworks no estado da técnica e pela
Tecnologia LingPON no estado da arte. Este trabalho apresenta o desenvolvimento
do Framework PON MicroPython 1.0, projetado especificamente para
microcontroladores compatíveis com o interpretador MicroPython. Durante o processo
de desenvolvimento, foram priorizadas a integração dos elementos do PON com os
periféricos mais comuns em microcontroladores, como General Purpose Input-Output
(GPIO), Analog-to-Digital Converter (ADC) e Pulse Width Modulation (PWM), além de
um mecanismo modular para comunicação de notificações entre dispositivos distintos.
Essa comunicação é viabilizada por meio de drivers de comunicação que preservam
uma interface de programação de alto nível, garantindo usabilidade e flexibilidade. Os
resultados obtidos incluem o desenvolvimento de duas aplicações práticas para
validação do framework. A primeira aplicação tem como objetivo avaliar o custo da
integração dos periféricos com os elementos do PON, tanto de maneira local quanto
distribuída entre dois microcontroladores. Já a segunda aplicação, denominada Air
Quality Monitor, explora o potencial do framework em simplificar a distribuição das
notificações em um cenário mais complexo, envolvendo quatro microcontroladores e
dois drivers de comunicação distintos. Ambas as aplicações demonstraram que o
framework facilitou o desenvolvimento, reduzindo o tamanho do código final e
mantendo uma interface de programação de alto nível. Contudo, os resultados
também evidenciaram um aumento na latência entre as ações e no consumo de
memória RAM, resultado das estruturas utilizadas pelo framework para fornecer as
abstrações dos componentes do PON. Além disso, este trabalho detalha o uso dos
elementos do framework, abrangendo tanto os integrados com periféricos quanto os
próprios drivers de comunicação desenvolvidos. A documentação apresentada
fornece uma base sólida para que outros desenvolvedores possam adotar e expandir
o uso do framework em diferentes contextos. Por fim, são propostas melhorias futuras
para o Framework PON MicroPython 1.0, com foco no aprimoramento do mecanismo
de comunicação.
Palavras-chave: Programação Orientada a Notificações; Microcontroladores;
Framework PON MicroPython; Sistemas Distribuídos.

ABSTRACT

The Notification-Oriented Paradigm (NOP) emerges as an innovative solution to
overcome recurring limitations in traditional programming paradigms, such as code
redundancy and high coupling. The realization of NOP concepts has been achieved
through state-of-the-art frameworks and the state-of-the-art LingPON Technology. This
work presents the development of the PON MicroPython 1.0 Framework, specifically
designed for microcontrollers compatible with the MicroPython interpreter. During the
development process, priority was given to integrating NOP elements with the most
common peripherals in microcontrollers, such as General-Purpose Input-Output
(GPIO), Analog-to-Digital Converter (ADC) and Pulse Width Modulation (PWM), in
addition to a modular mechanism for notification communication between different
devices. This communication is facilitated by communication drivers that maintain a
high-level programming interface, ensuring usability and flexibility. The results include
the development of two practical applications to validate the framework. The first
application aims to evaluate the cost of integrating peripherals with NOP elements,
both locally and distributed between two microcontrollers. The second application,
named Air Quality Monitor, explores the framework's potential in simplifying the
distribution of notifications in a more complex scenario involving four microcontrollers
and two distinct communication drivers. Both applications demonstrated that the
framework streamlined development, reducing the size of the final code while
maintaining a high-level programming interface. However, the results also highlighted
an increase in latency between actions and in RAM consumption, stemming from the
structures used by the framework to provide NOP component abstractions.
Additionally, this work details the use of the framework elements, encompassing both
those integrated with peripherals and the communication drivers developed. The
documentation provided establishes a solid foundation for other developers to adopt
and expand the use of the framework in various contexts. Finally, future improvements
for the PON MicroPython 1.0 Framework are proposed, focusing on enhancing the
communication mechanism.
Keywords: Notification-Oriented Paradigm; Microcontrollers; MicroPython NOP
Framework; Distributed systems.

1 INTRODUÇÃO
Este presente capítulo introdutório traz a motivação, justificativa, objetivos e
método deste Trabalho de Conclusão de Curso (TCC). Este trabalho de TCC está
focado principalmente no estado da técnica do chamado Paradigma Orientado a
Notificações (PON), particularmente propondo um Framework PON em MicroPython
para microcontroladores com ênfase na distribuição de notificações.
1.1 Motivação
O PON busca resolver alguns problemas presentes nos paradigmas
consolidados na indústria, como o Paradigma Imperativo (PI) e o Paradigma
Declarativo (PD). Os principais problemas tratados são oriundos de uma orientação a
percorrimentos e pesquisas, sendo tais problemas as redundâncias estruturais que
provocam a avaliação de expressões lógicas repetidas em diferentes partes da
aplicação e as redundâncias temporais resultando da reavaliação de expressões
lógicas várias vezes sem necessidade, bem como os acoplamentos daí decorrentes.
(SIMÃO; STADZISZ, 2009; NEVES, 2020)
O PON resolve estes problemas via um mecanismo de colaboração direta
entre entidades notificantes não acopladas e não redundantes, via uma organização
ímpar da computação realizada por elas, o que é detalhado no capítulo subsequente.
De antemão, entretanto, a materialização dos conceitos propostos pelo PON é
realizada por meio de frameworks no estado da técnica e pela Tecnologia LingPON
no estado da arte. Eis que os resultados alcançados nestes trabalhos são pertinentes
e mesmo animadores, ensejando um conjunto de novos trabalhos, como este
presente TCC.
1.2 Justificativa
O PON g uma solução ainda emergente para resolver alguns problemas
encontrados em paradigmas de programação tradicionais, salientando aqui a
Programação Orientada a Objetos (POO) do PI. Atualmente, no acima citado estado
da técnica, existem várias materializações dos conceitos propostos pelo PON por
meio de frameworks. No entanto, estes têm sido projetados para serem usados em
sistemas mais complexos e que executam em computadores ou processadores com
maior capacidade de computação (NEVES, 2020; FIGUEIREDO, 2022). Isto

14

justamente dificulta os seus usos em microcontroladores, nos quais os recursos
computacionais disponíveis são mais modestos (RASPBERRY, 2020).
Em suma, nenhum dos frameworks do PON utiliza as suas características
especificamente para microcontroladores, particularmente o desacoplamento implícito
das entidades, para poder abstrair a interação entre diferentes microcontroladores
utilizando alguma interface de comunicação. Ao ensejo, esse tipo de interface
costuma ser um desafio considerável para os iniciantes em sistemas embarcados.
Desta forma, um framework PON enxuto, orientado especificamente a dispositivos
embarcados e focado na abstração dos mecanismos de comunicação permitiria aos
desenvolvedores de aplicações embarcadas ter uma maior eficiência no momento de
implementar suas soluções.
1.3 Objetivos
Esta presente seção destaca o objetivo geral, bem como os daí derivados
objetivos específicos.
1.3.1 Objetivo Geral
Desenvolver um novo framework do PON em MicroPython que permita o
desenvolvimento de software neste paradigma para microcontroladores, com foco na
abstração dos mecanismos de comunicação e integração com os seus principais
periféricos.
De antemão, tal framework para PON em microcontroladores é denominado
de Framework PON MicroPython 1.0.
1.3.2 Objetivos Específicos
Com base ao objetivo geral, foram determinados os seguintes objetivos
específicos:
•

Desenvolver um novo framework PON em MicroPython com seus componentes
principais denominado Framework PON MicroPython 1.0.

•

Desenvolver um mecanismo para comunicação de notificações modular entre
os elementos Attribute, Premise e Condition do PON integrado ao Framework
PON MicroPython 1.0.

15

•

Desenvolver uma aplicação que utilize pelo menos três microcontroladores
Raspberry Pi Pico W para demonstrar o funcionamento do Framework PON
MicroPython 1.0 e o protocolo de comunicação.

•

Desenvolver a documentação de uso do framework.

tanto o ciclo de trabalho como a frequência do um gerador PWM a um
Attribute específico.

•

RF-06: O Framework PON MicroPython 1.0 deve permitir a
comunicação de notificações entre os elementos locais.

•

comunicação de notificações entre diferentes microcontroladores.

1.5 Método de Desenvolvimento
O trabalho foi estruturado em seis etapas principais: análise e estudo, projeto,
implementação, testes e resultados, documentação e conclusão.
Na primeira etapa, a análise e estudo, serão avaliadas as diferentes
linguagens (C++ e MicroPython) e plataformas viáveis para a implementação do
framework (Raspberry Pi Pico, ESP32, etc.). Também será realizada uma
investigação sobre sistemas de comunicação existentes, a fim de definir o protocolo
mais adequado para o mecanismo de comunicação a ser desenvolvido.
A segunda etapa, referente ao projeto, consiste no desenvolvimento do design
do framework e do mecanismo de comunicação. Nessa fase, serão criados diagramas
e especificações detalhadas, visando facilitar a implementação posterior. Na etapa de
implementação, os diagramas e especificações elaborados anteriormente serão
utilizados para a construção do framework na linguagem selecionada.
Durante a fase de testes e resultados, serão implementadas duas aplicações
principais para validar o framework proposto, cada uma explorando diferentes
cenários. A primeira aplicação, denominada "Sensores", envolve a interação com os
periféricos de um único microcontrolador. Já a segunda, uma versão distribuída do
AirQualityMonitor (BABU, 2022), utiliza três ou mais microcontroladores para testar o
framework em cenários distribuídos.

A quinta etapa envolve a criação de um manual de uso, fornecendo uma

2 FUNDAMENTAÇÃO TEÓRICA
A fundamentação teórica deste trabalho é composta por seis tópicos
principais, que fornecem o contexto necessário para o desenvolvimento do framework
e do mecanismo de comunicação propostos. Em suma, será abordado o conceito de
sistemas embarcados (seção 2.1), paradigmas de programação (seção 2.2), o próprio
paradigma orientado a notificações (seção 2.3) e seus frameworks (seção 2.4). Na
seção 2.5 são apresentados conceitos relativos ao PON aplicado aos sistemas
embarcados. Finalmente, na seção 2.6 a linguagem MicroPython é brevemente
apresentada.
2.1 Sistemas Embarcados
Os sistemas embarcados são dispositivos computacionais projetados para
executar funções específicas dentro de um sistema maior, muitas vezes operando em
tempo real e sob restrições de hardware e energia. Segundo Lee e Seshia (2017),
esses sistemas são caracterizados pela integração entre software e hardware,
resultando em soluções otimizadas para aplicações específicas, como dispositivos
móveis, automação industrial e veículos autônomos.
Para possibilitar a interação com sensores e atuadores, os sistemas
embarcados contam com diversos periféricos integrados, como GPIO, ADC, PWM,
UART e I2C. A seguir, são abordadas as principais características desses
componentes fundamentais:
•

GPIO: são fundamentais na comunicação entre microcontroladores e
periféricos externos, permitindo controle e monitoramento de sinais
digitais (RENESAS, 2025). Como entradas, os GPIOs podem ler
estados lógicos de dispositivos externos, como botões ou sensores
digitais. Como saídas, podem controlar dispositivos como LEDs, relés
ou outros componentes eletrônicos.

•

ADC: são dispositivos essenciais para a conversão de sinais
analógicos em digitais, permitindo que microcontroladores e outros
dispositivos digitais processem informações do mundo real, como
temperatura, tensão e som. (TEXAS INSTRUMENTS, 2025).

20

•

PWM: é uma técnica utilizada para controlar a potência entregue a
dispositivos eletrônicos, variando a relação entre tempo ligado e
desligado de um sinal periódico. Essa abordagem é amplamente
aplicada no controle de motores, na regulagem de brilho de LEDs e na
conversão de energia em fontes chaveadas (TEXAS INSTRUMENTS,
2025).

•

UART: é um protocolo de comunicação serial amplamente utilizado
para a transmissão de dados entre dispositivos eletrônicos. Diferente
de protocolos síncronos, o UART não requer um sinal de clock
compartilhado entre o transmissor e o receptor, utilizando apenas
linhas de transmissão e recepção para comunicação. Esse método é
comumente empregado em microcontroladores, sensores e módulos
de comunicação (TEXAS INSTRUMENTS, 2025).

•

I2C: é uma tecnologia de comunicação serial que utiliza apenas duas
linhas para transmitir e receber dados: uma para o sinal de clock e outra
para os dados . Ele é amplamente usado em sistemas embarcados,
devido à sua simplicidade e capacidade de conectar vários dispositivos
em um único barramento (TEXAS INSTRUMENTS, 2025).

Os sistemas embarcados são tradicionalmente programados em linguagens
C/C++. Não obstante, há outras linguagens de programação que emergem neste
contexto, sendo que aqui é destacado o MicroPython. Essas linguagens de
programação citadas fazem parte do paradigma imperativo. Justamente, a temática
de paradigmas para programação em geral é tratada na seção que segue.
2.2 Paradigmas de Programação
Um paradigma de programação é compreendido como um modelo ou método
para o desenvolvimento de programas computacionais, fundamentado em estruturas
linguístico-matemáticas e em um conjunto específico de princípios. Cada paradigma
é projetado para abordar determinados problemas, guiando-se por seus modelos e
princípios subjacentes. Dessa forma, cada paradigma possui um conjunto de regras
que pode torná-lo mais ou menos adequado para a resolução de problemas
específicos (ROY, 2012).

21

Os principais paradigmas de programação podem ser agrupados em quatro
categorias: o Paradigma Procedimental (PP), o Paradigma Funcional (PF), o
Paradigma Orientado a Objetos (POO) e o Paradigma Lógico (PL) (SCOTT, 2000;
WATT, 2004; BROOKSHEAR, 2006). Esses paradigmas são frequentemente
denominados como Paradigmas Dominantes. Além disso, considera-se em termos
gerais que o PP e o POO estão inseridos em um paradigma mais amplo, conhecido
como Paradigma Imperativo (PI), enquanto o PF e o PL fazem parte principalmente
de outro grande grupo, o Paradigma Declarativo (PD) (GABBRIELLI; MARTINI, 2010).
Dito de outra forma, os paradigmas dominantes podem ser classificados como
subconjuntos de dois paradigmas maiores: o Paradigma Imperativo (PI) e o
Paradigma Declarativo (PD) (BANASZEWSKI, 2009). Essa relação é representada
hierarquicamente, como ilustrado na Figura 1. Apesar de ser uma classificação útil
como visão geral, ela não é perfeita, pois os paradigmas compartilham características
entre si e frequentemente se aproximam mais de um paradigma dominante do que de
outro. Em resumo, essa organização hierárquica facilita as comparações, destacando
as características comuns entre os paradigmas (RONSZCKA, 2019).

às avaliações anteriores, caracterizando uma redundância temporal. Já as
redundâncias estruturais podem ser identificadas nos trechos destacados em verde,
onde a primeira avaliação lógica dessas duas expressões causais é estruturalmente
repetida no código, sendo executada duas vezes em cada ciclo. Além disso, essas
redundâncias podem estar dispersas no código, separadas por várias linhas, o que
dificulta sua identificação e mitigação, mesmo para desenvolvedores experientes,
tornando inviável tratá-las em códigos de grande escala. De forma cumulativa, tais
redundâncias podem resultar em desperdícios significativos de recursos de
processamento (PAN et al., 1998).
Além deste exemplo em PI, outros subparadigmas ou técnicas associadas ao
PI, PD ou à interseção entre ambos apresentam problemas semelhantes, como
discutido em RAYMOND (2003), BANERJEE et al. (1995), OSHIRO et al. (2021) e
RONSZCKA et al. (2017). Essas redundâncias são também observadas em
paradigmas como o procedimental, orientado a objetos e funcional, que compartilham
características semelhantes. Por outro lado, a programação lógico-declarativa,
embora opere em um nível mais abstrato, é implementada sobre o PI e, portanto, não
está isenta de redundâncias. Técnicas como a orientação a eventos, apesar de

23

contribuir para mitigar esses problemas, também não conseguem eliminá-los por
completo (RONSZCKA, 2019; OSHIRO et al., 2021).
Adicionalmente, os paradigmas vigentes frequentemente geram módulos
acoplados devido às redundâncias inerentes. Esse acoplamento exige conhecimento
técnico avançado em programação e modelagem para criar módulos parcialmente
desacoplados, visando organização, reaproveitamento e suporte ao processamento
paralelo ou distribuído. No entanto, mesmo com esses esforços técnicos, o
desacoplamento obtido raramente atinge um nível de granularidade suficiente para
otimizar o balanceamento de carga em sistemas paralelos ou distribuídos (OSHIRO
et al., 2021). Nesse contexto, o paradigma PON surge como uma alternativa que
busca, entre outras metas, eliminar redundâncias, contribuindo para a mitigação
desses desafios.

Inicialmente, tem-se os Fact Base Elements (FBEs) que contêm os Attributes
e Methods. Cada Attribute representa uma propriedade de um FBE, enquanto cada

executar suas Instigations associadas. Finalmente, cada Instigation executa os seus

notificação recebida, notifica apenas as Conditions pertinentes. Cada Condition que

realimentando assim o ciclo de inferência. Em tempo, naturalmente, as conexões de
notificação são estabelecidas em tempo de construção das entidades do PON
(SIMÃO; STADZISZ, 2009).

2.5 PON em sistemas embarcados
O uso de frameworks do PON em sistemas embarcados, caracterizados pela
ausência de sistemas operacionais tradicionais (Unix/Linux/Windows) e por recursos
computacionais limitados, ainda é pouco explorado. Essa lacuna representa um
obstáculo significativo para a adoção do PON nesses sistemas, pois adiciona um nível
adicional de complexidade, especialmente na interação com os periféricos do
microcontrolador, além de diminuir a abstração do PON.

29

Além disso, uma limitação comum a todos os frameworks existentes é a
implementação da distribuição dos elementos do PON exclusivamente por meio de
protocolos de rede. Isso inviabiliza a utilização do PON em cenários onde a
distribuição precisa ocorrer por outros meios de comunicação, como interfaces
Universal Asynchronous Receiver/Transmitter (UART) ou Inter-Integrated Circuit (I2C),
que são amplamente utilizadas em sistemas embarcados. Essa restrição reduz a
flexibilidade e a aplicabilidade do PON em ambientes com restrições de hardware ou
requisitos específicos de comunicação, destacando a necessidade de novas
abordagens que considerem a heterogeneidade dos sistemas embarcados.
2.6 MicroPython
No início dos anos 2010, o programador e físico britânico Damien George
percebeu uma lacuna no mundo da programação embarcada. Enquanto linguagens
como C e Assembly dominavam os microcontroladores, faltava uma opção mais
acessível e moderna para desenvolvedores e entusiastas. Inspirado na simplicidade
e no poder do Python, Damien decidiu criar uma versão enxuta da linguagem, capaz
de rodar em hardware de baixo custo e recursos limitados. Para financiar o projeto,
Damien lançou uma campanha no Kickstarter em dezembro de 2013, propondo não
apenas o software, mas também um hardware dedicado: a PyBoard, uma placa de
desenvolvimento otimizada para rodar MicroPython (DAMIEN et al, 2023).
Com esse impulso, o MicroPython foi oficialmente lançado em 2014,trazendo
uma implementação enxuta e eficiente da linguagem de programação Python 3, que
inclui um subconjunto reduzido da biblioteca padrão do Python e é otimizada para
operar em microcontroladores e em ambientes com recursos limitados (DAMIEN et al,
2023). Essa tecnologia consiste em um compilador e ambiente de execução completo,
projetado para executar diretamente sobre o hardware, sem a necessidade de
sistemas operacionais convencionais. Uma de suas características mais notáveis é o
Read-Eval-Print-Loop (REPL), um terminal interativo que permite executar comandos
imediatamente, facilitando o desenvolvimento e depuração de aplicações. O REPL
oferece funcionalidades como histórico de comandos, autocompletar com tabulação,
indentação automática e um modo de colagem de código, proporcionando uma
experiência fluida ao usuário.
O MicroPython foi desenvolvido com o objetivo de ser o mais compatível
possível com o Python tradicional (também conhecido como CPython). Assim,

30

conhecimentos em Python são diretamente aplicáveis ao uso do MicroPython. Além
disso, explorar o MicroPython em ambientes de hardware restrito contribui para uma
compreensão mais aprofundada da linguagem Python como um todo.
Além de implementar um conjunto essencial das bibliotecas principais do
Python, o MicroPython inclui módulos específicos, como o módulo "machine", que
permite o acesso direto ao hardware de baixo nível. Essa funcionalidade é
especialmente útil em sistemas embarcados, onde a interação com sensores,
atuadores e interfaces de comunicação, como GPIO, UART e I2C, é fundamental para
o desenvolvimento de aplicações.
Em suma, o MicroPython se destaca como uma ferramenta poderosa para a
programação em sistemas embarcados, unindo a simplicidade do Python com a
capacidade de operar em dispositivos com recursos limitados. Outro destaque, no
MicroPython, assim como no Python tradicional, são as funções lambda, as quais se
constituem em funções anônimas e curtas, definidas de maneira compacta. Elas são
úteis quando precisamos de uma função pequena e de curta duração, sem a
necessidade de definir um nome explícito. No Código 3, é apresentada a declaração
da função <soma= nas linhas 1 e 2, logo, na linha 6 g apresentada a mesma
funcionalidade em uma função lambda.

3 PROJETO
Nesta seção será apresentado o processo de definição e implementação do
próprio Framework PON MicroPython 1.0 proposto assim como o projeto das
aplicações de testes.
3.1 Projeto do framework
O projeto do framework foi estruturado em duas partes principais: projeto do
mecanismo de notificações e projeto do mecanismo de comunicação. A primeira parte
abrange o desenvolvimento dos componentes fundamentais do framework, incluindo
o mecanismo interno de notificações e sua interação com os pinos digitais do GPIO e
outros periféricos do microcontrolador. Já a segunda parte foca no mecanismo de
comunicação, responsável por viabilizar a troca de notificações entre diferentes
microcontroladores.
3.1.1 Projeto do mecanismo de notificações
Para a escolha da linguagem de programação a ser utilizada no
desenvolvimento do framework, foram consideradas duas opções principais: C++ e
MicroPython. Optou-se pelo MicroPython, uma alternativa relativamente recente no
domínio de programação para microcontroladores, que oferece um nível de abstração
mais alto em comparação ao C++, mantendo o suporte para recursos como
polimorfismo, herança múltipla e sobrecarga de operadores. Esses recursos são
fundamentais para a implementação do framework e tornam possível sua execução
em qualquer microcontrolador compatível com o interpretador MicroPython,
ampliando sua flexibilidade e aplicabilidade em diversos contextos de hardware.
Apesar de sua diferença em termos de desempenho em relação a linguagens como
C++, o MicroPython se destacou pela sua elevada portabilidade entre diferentes
microcontroladores. Isto permitira o framework ser executado em microcontroladores
que sejam compatíveis com uma versão do runtime do MicroPython, como a
Raspberry Pi Pico W (RASPBERRY, 2023)

código adicional para gerenciar as interações entre esses periféricos e o mecanismo

A utilização do GPIOAttribute elimina a necessidade de funções adicionais

Além disso, dispensa a criação de regras explícitas para sincronizar o estado do LED,

simplifica o desenvolvimento, reduz a complexidade do código e minimiza o risco de
erros relacionados à atualização manual de estados ou sincronização entre
componentes.
Quando o GPIOAttribute é utilizado no modo de entrada, seu valor não pode
ser atribuído diretamente, pois ele estará vinculado ao estado do pino, que será
atualizado por meio de uma interrupção. Essa interrupção é responsável por modificar
o valor do Attribute de acordo com o estado do pino e por disparar as notificações
associadas. A interrupção pode ser configurada para ser ativada em diferentes
condições: a cada mudança no estado do pino ou exclusivamente em bordas de
subida ou descida. No entanto, quando o GPIOAttribute é configurado no modo de
saída ele atua como qualquer Attribute booleano, com a diferença que o seu valor
também é representado no estado do pino associado.
Para a integração com o ADC do microcontrolador, foi projetado o
ADCAttribute, responsável por obter seu valor a partir da leitura de um pino analógico,
com o objetivo de facilitar o uso de potenciômetros ou sensores analógicos. Para sua
criação, é necessário apenas especificar o pino ao qual será associado. O valor do
ADC é obtido por meio de polling, com o intervalo de leitura configurável no momento
da construção. Além disso, considerando que é comum realizar deslocamentos e/ou
ajustes de escala no valor bruto do ADC, foi projetada a possibilidade de configurar

40

esses parâmetros diretamente no ADCAttribute. Com isso, o valor lido é
automaticamente ajustado, eliminando a necessidade de alterações adicionais para
seu uso posterior.
Para integrar o gerador PWM do microcontrolador ao sistema, foi
desenvolvido o PWMAttribute, um componente com comportamento diferenciado em
relação a um Attribute convencional. Esse componente foi projetado para gerenciar
dois parâmetros fundamentais do gerador PWM: a frequência e o ciclo de trabalho.
Para isso, o PWMAttribute incorpora dois Attributes separados, um para armazenar
cada parâmetro. Sempre que qualquer um desses Attributes é alterado, o
PWMAttribute é notificado e, automaticamente, aplica as mudanças ao gerador PWM
do microcontrolador. Esse mecanismo assegura que os parâmetros configurados
sejam refletidos de forma precisa no sinal gerado, sem necessidade de intervenções
manuais adicionais.

principal de encapsular os demais elementos do PON. Embora seu uso não seja
estritamente necessário para a definição ou funcionamento dos outros componentes
do framework, sua utilização é altamente recomendada. O uso de FBEs permite
organizar os componentes de maneira mais clara e coesa, facilitando a compreensão
e a manutenção das aplicações desenvolvidas. Essa abordagem também contribui
para uma estrutura mais modular, permitindo uma melhor reutilização de código em
projetos futuros. Ademais, isso respeita os princípios do PON desde sua origem, nos
quais FBEs são fundamentais.
3.2.2 Attribute
O framework possui diferentes implementações do componente Attribute, já
que além de sua versão simples (que somente armazena um valor), possui versões

fornecendo os parâmetros indicados no Quadro 3. É importante destacar que não é

automaticamente inferido no momento da sua criação, com base no valor inicial
fornecido. Os tipos de dado aceito são valores booleanos, strings, números inteiros
ou de ponto flutuante e outros tipos (classes) que sejam possíveis serializar no formato
JSON. Adicionalmente, se o componente precisa ser distribuído, deve-se definir um
valor para o seu id, que é do tipo inteiro de 32bits sem sinal, que deve ser único em

As Instigations são responsáveis por executar seus métodos em sequência
quando são ativadas. Sua construção é simples, pois envolve apenas fornecer uma
lista contendo todos os Methods que devem ser executados no momento de criação,
como demonstrado no exemplo do Código 14.
Código 14 – Exemplo de criação de uma Instigation.

mtA = lambda : print ("Executed A")
def mtB() :
print("Executed B" )
insA = Instigation([mtA, mtB, lambda : print("Executed C")])
Fonte: O autor.

Dessa forma, as Instigations oferecem uma maneira prática e eficiente de
agrupar e executar múltiplos Methods em uma ordem específica. Isso garante
flexibilidade e organização, tornando o processo de desenvolvimento mais
organizado.
3.2.7 Action
As Actions são responsáveis por executar as Instigations associadas a elas.
Em seu construtor, elas recebem uma lista das Instigations que devem ser executadas
quando acionadas. Isso permite que múltiplas sequências de métodos sejam
agrupadas e executadas de maneira controlada, de acordo com a necessidade da
aplicação. Um exemplo da criação de uma Action pode ser visto no Código 15.
Código 15 – Exemplo de criação de uma Action.
mtA = lambda : print ("Executed A")
mtB = lambda : print ("Executed B")
insA = Instigation([mtA, mtB, lambda : print("Executed C")])
insB = Instigation([lambda : print("Executed D")])
acA = Action([insA, insB])
Fonte: O autor.

Assim, as Actions proporcionam uma forma estruturada de orquestrar a
execução de várias Instigations de maneira controlada, permitindo que ações

complexas sejam realizadas com um único comando. Essa abordagem simplifica a
lógica da aplicação, tornando o código mais modular e fácil de entender.
3.2.8 Rule
A Rule é o componente central do framework, pois é responsável por unificar
toda a parte lógica para com a execução das ações, i.e., processamento l漃Āgico-causal.
Em seu construtor, ela recebe apenas uma Condition e uma Action, como pode ser
observado no Código 16. Quando a Condition é satisfeita, a Action correspondente é
executada.
Código 16 – Exemplo de criação de uma Rule.

mtA = lambda : print("Executed A")

lógicas, pois elimina a necessidade de variáveis intermediárias, permitindo que os
componentes sejam definidos e utilizados localmente dentro da aplicação. O exemplo
apresentado no Código 17 ilustra como essa definição direta permite resumir a
declaração da Rule do exemplo do Código 16.

3.2.9 Drivers de comunicação
Neste trabalho, foram implementados dois drivers de comunicação. O
primeiro, UARTDriver, é responsável por transmitir as notificações pela interface
UART do microcontrolador. O segundo, UDPDriver, permite a transmissão de
notificações através da rede Ethernet, utilizando o protocolo UDP sobre um sistema
de comunicação.
Os drivers de comunicação são responsáveis por fornecer a funcionalidade
de distribuição ao framework, pois são encarregados de transportar as notificações
através de um meio de transmissão específico. Eles foram projetados de forma
modular e independente do meio pelo qual a notificação é transmitida, permitindo
flexibilidade e facilitando a implementação de novos drivers conforme necessário.
Essa abordagem garante que o framework possa ser facilmente adaptado para
diferentes tipos de comunicação.
O UARTDriver foi implementado para ser de fácil utilização, com todos os seus
parâmetros de construção definidos com valores predefinidos. Essa abordagem visa
simplificar sua aplicação em cenários comuns, permitindo que o desenvolvedor o
utilize sem a necessidade de ajustes adicionais na maioria dos casos. No entanto,
para situações em que sejam necessárias modificações específicas na configuração
da interface UART, o driver oferece uma ampla gama de opções em seu construtor.

3.3.2 Aplicação de monitor de qualidade do ar
A aplicação Air Quality Monitor (AQM), conforme definida por Babu (2022), foi
empregada para validar a facilidade proporcionada pelo novo framework na
distribuição de aplicações. Esta aplicação monitora a qualidade do ar em um
determinado momento, avaliando os níveis de partículas suspensas no ar. Há dois
indicadores, PM2,5 e PM10, que correspondem à quantidade de partículas com
diâmetro máximo de 2,5 e 10 micrômetros. Nos testes, foram avaliados os indicadores
PM2,5 e PM10, e quanto menores seus valores, melhor a qualidade do ar naquele
momento.
Essa aplicação possui três elementos principais, ilustrados na Figura 13. O
AirQualitySensor é responsável por realizar as medições dos parâmetros de qualidade
do ar, especificamente os níveis de PM2,5 e PM10. O AirQualityMonitor atua como o
componente de processamento, encarregado de analisar os valores fornecidos pelos
sensores e determinar o estado geral da qualidade do ar. Por fim, o AirQualityInformer
é o elemento responsável por comunicar a qualidade do ar de cada parâmetro, de
forma que sejam interpretáveis para os usuários.

4.3 Considerações dos resultados
A análise dos resultados das duas aplicações, AirQualityMonitor e Sensors,
evidencia os impactos do Framework PON MicroPython 1.0 tanto em termos de
latência, uso de memória e de facilidade de uso. Em ambas as aplicações, o
framework demonstrou ser eficaz na simplificação do desenvolvimento, abstraindo
funções externas ao objetivo das aplicações em componentes reutilizáveis. Essa
vantagem é especialmente visível nas implementações distribuídas, onde o framework
eliminou grande parte da complexidade associada à configuração das interfaces de
comunicação entre microcontroladores e atualização de estados dos componentes.
No entanto, o uso do framework apresentou um custo em termos de
desempenho, com aumento na latência, principalmente observado na aplicação de
sensores. Assim como o aumento do uso de memória, que foi principalmente

73

observado na aplicação AQM. Esse impacto é esperado, dado o acréscimo do
mecanismo de notificações e da modularidade introduzida pelos drivers de
comunicação. Apesar disso, as medições demonstraram consistência nos tempos de
resposta, indicando que o framework mantém um comportamento previsível, essencial
em sistemas embarcados.
Dessa forma, os resultados sugerem que o Framework PON MicroPython 1.0
é uma solução promissora para o desenvolvimento de aplicações distribuídas, na qual
a redução do esforço de programação e a modularidade são mais importantes que o
impacto na latência e onde a capacidade de memória não seja um problema. A adoção
do framework permite criar sistemas distribuídos com maior facilidade, atendendo aos
requisitos de projetos modernos e complexo, sempre que a latência e uso de memória
seja compatível com os requisitos.

5 CONCLUSÃO
O desenvolvimento deste trabalho de conclusão de curso representou a
aplicação prática de uma vasta gama de conhecimentos adquiridos ao longo do curso
de Engenharia de Computação. A base fornecida pela engenharia de software
possibilitou um planejamento sólido e estruturado, permitindo que o projeto e a
implementação dos diferentes componentes e aplicações ocorressem sem problemas
significativos. A integração de conceitos de eletrônica e sistemas embarcados foi
essencial para compreender as particularidades e restrições desses sistemas,
promovendo melhorias no processo de desenvolvimento e resultando em soluções
mais eficientes. Além disso, as técnicas de análise de dados foram cruciais para a
medição e avaliação rigorosa do desempenho do framework, garantindo a validação
dos objetivos propostos.
O resultado deste trabalho é a implementação do Framework PON
MicroPython 1.0, que preenche uma lacuna nos frameworks PON para rodar em
sistemas microcontrolados. Esse novo framework possibilita, justamente, a análise
das vantagens e desvantagens do PON neste contexto de microcontrolados, mas com
a vantagem de utilizar uma linguagem de programação de alto nível. Além disso, o
mecanismo de distribuição de notificações desenvolvido permite a avaliação de casos
de uso distribuídos entre múltiplos microcontroladores. Por fim, destaca-se que,
devido ao uso do MicroPython, as aplicações podem ser executadas diretamente em
diferentes arquiteturas microcontroladas, desde que compatíveis com a linguagem.
5.1 Resultados
Durante todo o desenvolvimento deste trabalho foram considerados os
objetivos específicos definidos na Seção 1.3.2 para garantir o cumprimento do objetivo
geral definido na Seção 1.3.1. A seguir, são detalhadas as ações realizadas para
atingir cada um desses objetivos.
O primeiro objetivo foi desenvolver o Framework PON MicroPython 1.0,
incluindo todos os seus componentes principais (Attribute, Premise, Condition, Rule,
Action, Instigation, Method). Esse framework foi projetado e implementado em sua
totalidade como demonstrado nas aplicações de testes, além de integrar componentes
específicos que facilitam a interação com periféricos dos microcontroladores.

75

Outro ponto central foi a criação de um mecanismo modular para
comunicação de notificações entre os elementos Attribute, Premise e Condition do
framework. Para isso, foi desenvolvida uma interface modular que permite a
comunicação entre microcontroladores por meio de diferentes meios físicos e
protocolos. Essa abordagem inclui a implementação de drivers, como o UARTDriver
e o UDPDriver, que permitem sua adaptação a diferentes cenários de comunicação
distribuída.
A aplicação prática do framework em um ambiente com pelo menos três
microcontroladores foi demonstrada através do desenvolvimento da aplicação Air
Quality Monitor. Essa aplicação utilizou quatro microcontroladores Raspberry Pi Pico
W e dois drivers de comunicação distintos, ilustrando a capacidade do framework de
integrar múltiplos dispositivos e compartilhar informações em vários meios de
comunicação.
Por fim, a documentação do Framework PON MicroPython 1.0 foi
desenvolvida com base na Seção 3.2 e est愃Ā disponível no arquivo <README.md= do
repositório oficial4 do kernel do framework. Essa documentação foi estruturada para
ser acessível e prática, fornecendo informações completas sobre a instalação,
configuração, uso e exemplos práticos do framework. Essa etapa é fundamental para
garantir que outros desenvolvedores possam adotar o framework de maneira rápida e
eficiente, contribuindo para a disseminação e uso da tecnologia desenvolvida.
Essas ações mostram que todos os objetivos específicos foram alcançados
de forma satisfatória, contribuindo para o avanço no uso do PON em sistemas
embarcados.
5.2 Trabalhos futuros
Este trabalho abre portas para diversas possibilidades de desenvolvimento e
aprimoramento futuro, evidenciando o potencial e a flexibilidade do framework
desenvolvido. Entre as direções mais relevantes estão a implementação de novos
drivers de comunicação, como suporte ao Bluetooth Low Energy (BLE), expandindo
as opções de conectividade para aplicações em diferentes casos de uso. Além disso,
o desenvolvimento de mais aplicações utilizando o framework poderá não apenas

O Framework PON MicroPython 1.0 desenvolvido demonstra uma aplicação
prática e inovadora do Paradigma Orientado a Notificações (PON), tornando-o
acessível a uma ampla variedade de microcontroladores graças ao uso de
MicroPython. A integração direta com periféricos relevantes e a modularidade do
mecanismo de distribuição reforçam sua flexibilidade e adaptabilidade, permitindo
futuras expansões com interfaces de comunicação adicionais sem requerer alterações
no código-base. Dessa forma, este trabalho não apenas cumpre seus objetivos
iniciais, mas também contribui para facilitar o desenvolvimento de sistemas
embarcados distribuídos, promovendo escalabilidade, modularidade e eficiência no
uso do PON.
