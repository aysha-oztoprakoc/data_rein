RESUMO

Sistemas Baseados em Regras (SBR) são sistemas computacionais que organizam
o conhecimento em elementos da base de fatos e regras, nos quais alterações nos
elementos da base de fatos causam a aprovação/desaprovação de diferentes regras
ao longo do fluxo de execução de um programa. SBRs são normalmente
implementados por percorrimento de estruturas de dados (computacionalmente
custosas) para verificar se os elementos da base de fatos mudaram e para saber
quais regras devem ser aprovadas ou desaprovadas com base nessas mudanças,
causando redundâncias temporais (i.e., repetição do cálculo de expressões
booleanas) e estruturais (i.e., repetição de código). Nesse sentido, o Paradigma
Orientado a Notificações (PON) propõe a divisão do programa em entidades
notificantes “inteligentes”, as quais notificam suas dependências ao sofrerem
alterações nos seus estados internos, eliminando pesquisas com redundâncias
temporais e estruturais para a inferência de regras. Em suma, ao ter seu estado
interno alterado, um elemento da base de fatos notificará apenas as regras
pertinentes a ele, isto é, as regras que dependem dele, para serem
aprovadas/ativadas ou desaprovadas/desativadas. O propósito deste trabalho é, por
meio da álgebra, formalizar a dependência entre regras e os elementos da base de
fatos de um sistema PON como a multiplicação de matrizes esparsas por vetores
densos, ou SpMV (Sparse Matrix-Vector Multiplication). A partir da formalização, foi
desenvolvido um novo framework do PON em C++, chamado de MBRIS 0.1 (MatrixBased Rule Inference System), o qual implementa um novo mecanismo de
inferência orientado a notificações, inspirado em multiplicação de matrizes para
animar as notificações. Isto em detrimento da forma usual de implementar na qual
uma entidade tem o endereço das notificáveis, o PON, como nos Frameworks PON
que, ao ensejo, permitiram linguagens usuais (e.g., C++, Java e C#) trabalharem
orientadas a notificações. Além da inovação na forma de notificar, visando aproveitar
o hardware de placas de vídeo, especializado em realizar operações com matrizes
de forma altamente paralelizável, foi implementado um kernel de OpenCL no MBRIS
para ser capaz de executar o fluxo de notificações do PON em placa de vídeo. Por
fim, foi implementada uma aplicação de simulação de sensores como prova de
conceito utilizando o MBRIS, e comparou-se o desempenho da aplicação em MBRIS
com a mesma aplicação desenvolvida utilizando o Framework PON C++ 4.0. Ainda
que os resultados do experimento realizado não tenham sido promissores em
termos de desempenho, com a implementação em Framework MBRIS 0.1
apresentando tempos de execução superiores aos da implementação em
Framework PON C++ 4.0 em todos os cenários, eles demonstram a viabilidade
técnica de implementar o fluxo lógico-causal de notificações do PON por meio de
operações de SpMV.

ABSTRACT

Rule-Based Systems (RBS) are computational systems that organize knowledge into
fact-base elements and rules, in which changes in fact-base elements cause the
approval/disapproval of different rules throughout the execution flow of a program.
RBSs are typically implemented by traversing (computationally expensive) data
structures to check whether fact-base elements have changed and to know which
rules should be approved or disapproved based on these changes, causing temporal
(i.e., repetition of the calculation of boolean expressions) and structural (i.e.,
repetition of code) redundancies. In this sense, the Notification Oriented Paradigm
(NOP) proposes the division of the program into “intelligent” notifying entities, which
notify their dependencies when their internal states change, eliminating searches
with temporal and structural redundancies for rule inference. In short, when its
internal state changes, an element of the fact base will notify only the rules that are
relevant to it, that is, the rules that depend on it, to be approved/activated or
disapproved/deactivated. The purpose of this work is to formalize, through algebra,
the dependency between rules and the elements of the fact base of a NOP system
as the multiplication of sparse matrices by dense vectors, or SpMV (Sparse MatrixVector Multiplication). From the formalization, a new NOP framework was developed
in C++, called MBRIS 0.1 (Matrix-Based Rule Inference System), which implements a
new notification-oriented inference mechanism, inspired by matrix multiplication to
animate notifications. This is to the detriment of the usual way of implementing in
which an entity has the address of the notifiable entities, the NOP, as in the NOP
Frameworks that, at the time, allowed usual languages (e.g., C++, Java and C#) to
work in a notification-oriented manner. In addition to the innovation in the notification
method, aiming to take advantage of the graphics card hardware, specialized in
performing operations with matrices in a highly parallelizable way, an OpenCL kernel
was implemented in MBRIS to be able to execute the NOP notification flow on the
graphics card. Finally, a sensor simulation application was implemented as a proof of
concept using MBRIS, and the performance of the application in MBRIS was
compared with the same application developed using the Framework NOP C++ 4.0.
Although the results of the experiment carried out were not promising in terms of
performance, with the implementation in the MBRIS 0.1 Framework presenting
superior execution times to the implementation of the operations in the PON C++ 4.0
Framework in all scenarios, they demonstrate a technique for implementing the
logical-causal flow of NOP notifications through SpMV scenarios.
Keywords: Notification Oriented Paradigm; sparse matrices; SpMV; OpenCL.

1 INTRODUÇÃO
Este primeiro capítulo visa trazer a motivação, justificativa, objetivos e
método deste Trabalho de Conclusão de Curso (TCC). O foco deste TCC está tanto
no estado da arte no tocante à formalização do Paradigma Orientado a Notificações
(PON) quanto na proposição de uma nova abordagem inovadora para a
implementação do fluxo de notificações a partir da multiplicação de matrizes.
1.1 Motivação
O Paradigma Orientado a Notificações (PON) é um novo paradigma de
programação que visa resolver algumas redundâncias dos vigentes, em especial do
Paradigma Imperativo (PI), composto principalmente pelo (sub) Paradigma
Procedimental (PP) e pelo (sub) Paradigma Orientado a Objetos (POO), e do
Paradigma Declarativo (PD), que pode ser dividido entre o (sub) Paradigma Lógico
(PL) e o (sub) Paradigma Funcional (PF) (SIMÃO; STADZISZ, 2008). O PON traz
uma inovação ao realizar computações pela colaboração de entidades mínimas
notificantes das quais derivam propriedades como a não redundância causal (i.e.,
evitamento de reavaliação desnecessária de expressões lógicas) e a não
redundância estrutural (i.e., evitamento de repetição de código), o que resulta em
bom desempenho de tempo de execução (SIMÃO; STADZISZ, 2009; NEVES 2020).
Tradicionalmente e por herança da primeira grande materialização do PON
em âmbito de software (BANASZEWSKI, 2009), o mecanismo de inferência do PON,
isto é, o mecanismo de notificações do PON, é implementado em software através
de chamadas de funções que partem das entidades notificantes para as entidades
notificadas, conforme será exposto no próximo capítulo. Embora seja uma forma
simples de implementar o ciclo de notificações em software e que já demonstrou
resultados satisfatórios, tal implementação é inviável para a execução de código
PON em plataformas que não sejam CPUs (Central Processing Unit), conforme
também será exposto no próximo capítulo.
Não obstante, mesmo que a teoria do PON preveja um paralelismo
intrínseco ao paradigma, as arquiteturas vigentes de CPUs não são capazes de lidar
com processamento altamente paralelo, impedindo que aplicações do PON em
software alcancem o paralelismo almejado pelo paradigma. Em contrapartida, as
arquiteturas de GPUs (Graphics Processing Unit) são pensadas para trabalhar com

14

um grande volume de pequenas tarefas paralelas. Existe, portanto, uma brecha para
emergir um novo modelo de execução para o PON, que torne viável a execução de
programas PON em GPU, a fim de alcançar, em software, o potencial de paralelismo
do paradigma.
Por fim, torna-se pertinente ressaltar que a formalização do modelo do PON
poderia ajudar a melhor compreendê-lo, bem como daí intuir novas formas de
inferência por notificação. Dito de outra maneira, tal formalização não determinaria
como o mecanismo de notificações deve ser implementado em software, mas sim
permitiria e ensejaria o surgimento de implementações alternativas do mecanismo
para diferentes cenários.
1.2 Justificativa
A complexidade assintótica do mecanismo de notificações do PON no pior
caso, mesmo que tal caso seja impraticável, é da ordem de 𝑂(𝑛3 ) (SIMÃO;
STADZISZ 2008), sendo exatamente a mesma complexidade do algoritmo
tradicional de multiplicação de matrizes, o que já indicaria uma certa equivalência
entre o processamento lógico-causal do PON com a multiplicação de matrizes. Não
obstante, ao entender que o pior caso do PON é uma situação em que todas as
entidades do PON se notificam entre si e que isso raramente ocorre na prática,
pode-se facilmente visualizar um grafo de interdependência das entidades de uma
aplicação PON altamente esparso com um caso médio que seria O(n)
(BANASZEWSKI 2009; RONSZCKA et al., 2015; RONSZCKA, 2019). Neste caso,
naturalmente, o PON alcança um desempenho muito melhor do que o pior caso e
muitas vezes superior aos paradigmas vigentes. Grafos esparsos podem ser
representados como matrizes esparsas, e existem algoritmos de multiplicação de
matrizes esparsas cuja complexidade assintótica é da ordem de 𝑂(𝑁𝑁𝑍), sendo
𝑁𝑁𝑍 (Number of Non-Zeros) uma constante que indica o número de elementos nãonulos de uma matriz (GAO et al., 2024), corroborando com a ideia de traduzir o fluxo
de notificações do PON em operações com matrizes.
Nesse sentido, ao se traduzir o mecanismo de notificações do PON para
operações com matrizes esparsas, é possível não apenas formalizar um modelo
matemático do PON, como também mais facilmente paralelizar a execução do fluxo

de notificações, fazendo uso dos avanços recentes no hardware de placas de vídeo

2.1 Paradigmas de Programação
Paradigmas de programação são arquétipos que definem formas de
desenvolver soluções de software, no tocante ao desenvolvimento de programas,
mais precisamente.

Cada paradigma possui seu próprio conjunto de técnicas e

conceitos fundamentais que os tornam únicos e (mais ou menos) adequados para
solucionar determinados problemas cotidianos, matemáticos ou mesmo puramente
computacionais, dentre outros (VAN ROY, 2004).
Existem hoje quatro paradigmas ditos dominantes na indústria e academia: o
Paradigma Procedimental (PP), o Paradigma Orientado a Objetos (POO), o
Paradigma Lógico (PL) e o Paradigma Funcional (PF) (SCOTT, 2000; WATT, 2004;
BROOKSHEAR, 2006). Para fins de simplificação, ainda que haja interseções, é
possível enxergar duas grandes categorias de paradigmas que englobam os demais,
ou dois paradigmas mais amplos compostos de sub-paradigmas: o Paradigma
Imperativo (PI), o qual engloba o PP e o POO, e o Paradigma Declarativo (PD),
composto pelos PL e PF (GABBRIELLI; MARTINI, 2010). Embora não seja perfeita,
essa relação de organização hierárquica entre os paradigmas facilita comparações
entre os mesmos, destacando as características comuns entre eles (RONSZCKA,
2019).
Embora muito poderosos e amplamente utilizados, os paradigmas do PI
frequentemente

STADZISZ, 2009). O Código 1 ilustra um exemplo corriqueiro de redundâncias

2.2 Paradigma Orientado a Notificações
O Paradigma Orientado a Notificações (PON) é um paradigma de
programação emergente que herda algumas características do PI e do PD, ao
mesmo tempo que visa solucionar alguns dos problemas inerentes a esses
paradigmas. No PON, há uma separação entre as entidades facto-execucionais (i.e.,
estados dos elementos e as ações que alteram seus estados) e as entidades lógicocausais (i.e., regras de decisão sobre quais ações serão executadas com base nos
relacionamentos entre entidades e seus estados) (RONSZCKA, 2019).
O primeiro grupo é formado por Attributes (atributos) e Methods (métodos)
agrupados em instâncias de Fact Base Elements (FBEs, elementos da base de
fatos). Por sua vez, no segundo grupo há Rules (regras) definidas a partir de
Conditions (condições) que agrupam Premises (premissas), bem como Actions
(ações) que agrupam Instigations (instigações) (RONSZCKA, 2019; NEVES 2021). A
Figura 1 exemplifica o agrupamento das entidades do PON e seus relacionamentos.

20

Figura 1 - Um exemplo de FBE, Rule e seus elementos

Fonte: Neves (2021)

O mecanismo de notificações do PON, ponto central de sua inovação,
consiste em cada uma dessas entidades notificarem suas sucessoras no ciclo de
notificações ao mudarem de estado. Os FBEs definem as entidades factuais de um
programa, com o estado sendo definido por Attributes e o seu comportamento por
Methods. Ao mudarem de valor, os Attributes notificam as Premises pertinentes que
dependem deles. Uma Premise é uma comparação entre Attributes ou entre
Attributes e constantes, assim, quando notificada, ela reavalia sua comparação e
notifica as Conditions que dependem dela caso seu estado interno mude. Conditions
são expressões lógicas entre Premises, notificando suas Rules associadas ao
mudarem de estado. Rules, ao serem aprovadas pela Condition associada,
executam sua Action, que por sua vez executam as suas Instigations. Finalmente,
Instigations são agrupamentos de chamadas de Methods, os quais podem modificar
Attributes, reiniciando o ciclo. Em tempo, naturalmente, as conexões de notificação
são estabelecidas em tempo de construção das entidades do PON (SIMÃO;
STADZISZ, 2009; RONSZCKA, 2019; NEVES 2021).

por uma Instigation que executa o Method mtProcess do FBE Sensor. O

As materializações vigentes do PON podem ser divididas entre o estado da
arte (i.e., prototipais) e o estado da técnica (i.e., estáveis). O estado da arte do PON
é a Tecnologia LingPON, atualmente em sua versão 3.0, a qual é composta por uma
linguagem de programação em alto nível específica para o PON, a NOPL 3.0
(Notification Oriented Programming Language), o Grafo PON Modular como
representação intermediária, o método de compilação para o PON (MCPON)
(RONSZCKA, 2019) e diferentes alvos de compilação (CHIERICI; SKORA; SIMÃO,
2022). Em particular, o Grafo PON permite que diferentes linguagens de
programação do PON sejam compiladas para diferentes alvos de compilação de
maneira transparente e desacoplada (RONSZCKA, 2019).
Apesar de ainda não ser aplicável industrialmente, a Tecnologia LingPON
3.0 já se mostrou mais flexível e poderosa do que a anterior, tendo como ponto
central de inovação um Grafo PON Modular. Este Grafo PON Modular permite que
alvos de compilação e/ou linguagens específicas utilizem recursos do Grafo PON
desenvolvido exclusivamente para eles e elas sem impactar com outros alvos e
linguagens, através da modularidade. Além disso, a NOPL 3.0, diferentemente da
versão 2.0, foi demonstrada ser Turing-completa (i.e., é teoricamente capaz de
resolver qualquer problema computacional) (CHIERICI; SKORA; SIMÃO, 2022;
CHIERICI, 2022).

22

O estado da técnica do PON, por sua vez, é composto por diferentes
frameworks PON desenvolvidos em linguagens de programação já consolidadas na
indústria, entre eles citam-se os recentes frameworks PON C++ 4.0 (NEVES, 2021),
PON C++ 4.5 (LEDESMA; SIMÃO, 2022) e PON C++ 4.0 IoT (FIGUEIREDO, 2022),
o Framework PON Erlang/Elixir (NEGRINI et al., 2019), o Framework PON C# IoT
(OLIVEIRA, 2019) e o Framework PON MicroPython 1.0 (LEDESMA, 2025), cada
qual com suas vantagens e limitações, mas sendo o Framework PON C++ 4.0 até
hoje a materialização com melhor desempenho geral e mais estável do PON
(NEVES, 2021; LEDESMA; SIMÃO, 2022).
Embora os frameworks PON tenham avançado significativamente em
questões de qualidade de código, desempenho, distribuição, paralelismo e
programação em alto nível ao longo dos anos, eles ainda seguem o mesmo princípio
de implementação do fluxo de notificações (quando não estão distribuídas em rede)
do PON proposto pelo primeiro grande framework PON, o Framework PON C++ 1.0,
derivado do Framework PON C++ prototipal elaborado por J. M. Simão
(BANASZEWSKI, 2009). Tanto o Framework PON C++ 1.0 quanto o Framework
PON C++ prototipal são baseados em chamadas de função das entidades
notificadas pelas entidades notificantes. Apesar de ser um modelo de fácil
implementação e que funciona para demonstrar as qualidades do PON, a teoria do
PON não exige que o fluxo de notificações do PON seja implementado dessa
maneira, e tal modelo de execução seria impróprio para execução de código PON
em plataformas que não sejam CPUs, conforme explicado a seguir.
Quando se fala em paralelismo, GPUs tendem a alcançar um desempenho
superior a CPUs em tarefas simples, mas desde que elas sejam altamente
paralelizáveis. Isto assim se dá porque enquanto CPUs são compostas por poucos
núcleos de processamento, mas de alto desempenho, GPUs são compostas por
muito núcleos de processamento de baixo desempenho. Tal característica faz com
que GPUs sejam ideais para cenários com um volume elevado de operações
simples e independentes entre si, enquanto CPUs sejam ideais para tarefas mais
complexas, porém sequenciais.
Assim, existe hoje uma brecha para emergir um novo estado da arte em
PON que explore a execução do ciclo de notificações em GPU. Embora um modelo
que traduza o cálculo lógico-causal do PON para operações viáveis de serem
executadas em GPU possa causar uma latência maior para uma notificação isolada,

23

o mesmo seria capaz de processar um volume muito elevado de notificações
simultaneamente, o que pode ser desejável em algumas aplicações.

2.3.3 Considerações sobre matrizes esparsas e SpMV
Matrizes esparsas são, por si só, uma ferramenta para modelar problemas a
partir de álgebra linear, da mesma forma que grafos são uma ferramenta para
modelar problemas sob uma ótica computacional. Muito embora a mera
representação das informações em matrizes esparsas não represente um ganho
além da otimização de armazenamento, a utilização de algoritmos como o SpMV
permite que a estrutura e as características de diferentes formatos de
armazenamento de matrizes esparsas sejam exploradas para resolver problemas de
diversas áreas de forma paralela e eficiente (GAO et al., 2024).
Nesse sentido, ao traduzir as relações de notificação entre entidades do ciclo
lógico-causal do PON para matrizes esparsas e operações de SpMV, torna-se
possível a execução de programas PON de maneira extraordinária por meio da
multiplicação de matrizes esparsas por um vetor. Ainda, esta tradução traria um
modelo matemático para o fluxo de notificações lógico-causal do PON, fazendo uso
de álgebra linear para tal.

2.4 Arquitetura de placas de vídeo
Uma placa de vídeo (GPU) é um tipo especial de processador projetado para
processamento gráfico e tarefas com processamento altamente paralelo (NVIDIA,
2025). Em contrapartida, uma CPU, considerando as arquiteturas tradicionais
inspiradas em von Neumann (LINHARES, 2015), é um processador projetado para
executar tarefas majoritariamente sequenciais o mais rápido possível (NVIDIA,
2025). Em termos de divisão dos recursos de hardware, considerando que fossem
utilizados a mesma quantidade de transistores para criar uma CPU e uma GPU,
enquanto a CPU possuiria poucos núcleos de alto desempenho, a GPU seria
formada por centenas ou milhares de núcleos de baixo desempenho. A Figura 6
ilustra a divisão dos recursos de um chip para CPUs e GPUs.

compartilhada por vários núcleos numa GPU. Além disso, cada núcleo, unidade de
controle e memória cache L1 numa CPU é muito maior do que os mesmos
elementos numa GPU, implementando operações e pipelines mais complexas em
relação à GPU, além de, normalmente, possuírem uma frequência de clock maior.
Tais características fazem com que um núcleo de CPU execute um número muito
maior de instruções do que um núcleo de GPU em um mesmo intervalo de tempo.

28

No entanto, por possuir uma quantidade muito maior de núcleos, uma GPU é capaz
de executar muito mais tarefas paralelamente do que CPUs.
Em termos de modelos de execução, dizemos que GPUs seguem o modelo
Single Instruction, Multiple Data (SIMD), isto é, uma mesma operação é executada
sobre diferentes dados (BERG; SIEGEL, 1991). Por outro lado, CPUs, quando
compostas por múltiplos núcleos (i.e., CPUs multicore), seguem o modelo Multiple
Instruction, Multiple Data (MIMD), ou seja, diferentes operações são executadas
para diferentes dados (BERG; SIEGEL, 1991). Em suma, embora seja menos
flexível do que o modelo MIMD, o modelo SIMD, aliado à grande quantidade de
núcleos de GPUs, permite que GPUs possam realizar operações simples sobre um
grande volume de dados de maneira rápida e altamente paralela. Um exemplo é
justamente a operação SpMV, na qual, para o formato CSR visto anteriormente,
cada linha da matriz pode ser multiplicada pelo vetor em um núcleo diferente da
GPU.
Dada a baixa flexibilidade do modelo SIMD, GPUs normalmente não são
utilizadas para executar aplicações inteiras, mas sim apenas uma parte delas, isto é,
a parte que se beneficiaria do paralelismo massivo de uma GPU, com o restante da
aplicação executando em CPU. Esta colaboração entre CPU e GPU forma um
sistema heterogêneo CPU-GPU, no qual o fluxo principal de uma aplicação é
executada em CPU, como partes pontuais dela executando em GPU, sob a forma de
compute kernels. É pertinente ressaltar que, dependendo da aplicação, pode ser
necessário transferir dados entre CPU e GPU, adicionando um overhead no tempo
de execução da aplicação que depende diretamente do hardware utilizado. Assim,
ao projetar uma aplicação para um sistema heterogêneo CPU-GPU, é importante
levar em conta o overhead de uma transferência de dados entre CPU e GPU e
buscar minimizar o número de transferências, caso contrário, o desempenho geral
da aplicação no sistema CPU-GPU pode ser pior do que se ela fosse executada
somente em CPU, mesmo com o elevado grau de paralelismo de uma GPU.
2.5 OpenCL
OpenCL (Open Computing Language) é um padrão aberto e multiplataforma
para programação paralela em sistemas heterogêneos, como CPUs, GPUs, DSPs
(Digital Signal Processors) e FPGAs (Field-Programmable Gate Array). Desenvolvido
inicialmente pela Apple e mantido pelo Khronos Group, o OpenCL permite que

29

aplicações aproveitem o potencial de processamento paralelo de múltiplos
dispositivos, otimizando o desempenho em tarefas intensivas, como processamento
de imagens, simulações científicas e aprendizado de máquina (KHRONOS, 2025).
Sua flexibilidade reside na capacidade de abstrair diferenças arquiteturais,
oferecendo uma interface unificada para gerenciamento de memória, execução de
kernels (funções paralelas) e sincronização.
2.5.1 Arquitetura do OpenCL
A especificação do OpenCL define quatro modelos abstratos para
organização do hardware e execução de programas: modelo de plataforma, modelo
de execução, modelo de memória e modelo de programação. A Figura 7 ilustra o

pelo host para aquele compute kernel.
O OpenCL divide a memória em uma hierarquia de quatro níveis. No primeiro
nível, a memória global, compartilhada por todos os work-items e com alta latência.
No segundo, a memória constante, também acessível por todos os work-items, mas
sendo restrita apenas a operações de leitura (readonly). O terceiro nível é formado
pela memória local, acessível apenas dentro de um mesmo work-group. Por fim, o
último nível consiste na memória privada, exclusiva para cada work-item e, portanto,
com a menor latência entre as demais. Ainda, é pertinente ressaltar que transferir
dados entre diferentes níveis da hierarquia de memória, ou ainda transferir dados
entre o host e os dispositivos, adiciona um overhead durante a execução do
programa, sendo que tal overhead depende diretamente do hardware utilizado,
conforme o que foi exposto na seção anterior.
Finalmente, o modelo de programação do OpenCL consiste numa linguagem
de programação baseada no C99 (OpenCL C), utilizada para o desenvolvimento de
kernels que serão executados nos dispositivos, e em uma API para o host escrita em
C ou C++. A combinação destas ferramentas permite que desenvolvedores utilizem
um host e um ou mais dispositivos como um sistema unificado de computação
paralela (KHRONOS, 2025).
2.5.2 Considerações sobre OpenCL, SpMV e PON
O OpenCL se mostra como uma ferramenta facilitadora para programação
paralela em hardwares aceleradores (KHRONOS, 2025), sendo agnóstica em
termos de paradigmas de programação, o que permite que seu uso seja combinado
com o uso do PON, bastando, para isso, a existência de uma materialização do PON
implementada a partir do OpenCL. Tal materialização possibilitaria a execução de
programas PON em hardwares com execução altamente paralela.
Um código em OpenCL é um compute kernel a ser executado pelo dispositivo
escolhido, sendo que uma operação de SpMV é um compute kernel, o que a torna
ideal para o modelo de execução do OpenCL. Dessa forma, traduzir o mecanismo
de notificações do PON para operações de SpMV é uma forma de viabilizar o
desenvolvimento de uma materialização do PON a partir do OpenCL. Esta nova
materialização executaria o fluxo de notificações de forma extraordinária e não

31

usual, por meio da multiplicação de matrizes esparsas por um vetor, e graças ao
OpenCL, tal execução poderia ser executada em GPU de maneira altamente
paralela, alcançando o paralelismo almejado pelo paradigma.

3 INFERÊNCIA DO PON BASEADA EM MULTIPLICAÇÃO DE MATRIZES
Nesta seção é apresentada a formalização do mecanismo de inferência para
o PON baseado na multiplicação de matrizes esparsas por um vetor, denominado
matriz de ativadores, e a implementação do framework MBRIS 0.1 proposto, à luz da
formalização da matriz de ativadores. Entretanto, antes de explorar a formalização
da matriz de ativadores, é necessário primeiro compreender como seria possível
executar o ciclo de notificações do PON a partir de operações de SpMV.
3.1 PON a partir de SpMV
Esta seção explica como se executa o ciclo de notificações do PON a partir
de operações de SpMV, apresentando um exemplo para tal.
Inicialmente, foca-se na parte lógico-causal do paradigma, cujo fluxo de
notificações começa na mudança de estado de um dado Attribute, evolui para um
conjunto de Premises, evolui ainda para um conjunto de Conditions e termina na
possível aprovação de um conjunto de Rule. Com isto em mente, mapeia-se dois
vetores de uma operação de SpMV para os pontos de entrada e saída do fluxo
lógico-causal do PON: um vetor de Attributes e um vetor de resultado da aprovação
das Rules. Além disso, a matriz da operação de SpMV representaria as demais
entidades lógico-causais do PON (i.e., Premises, Conditions e Rules elas mesma).
Neste quadro, o fluxo de notificações do PON ocorre por meio da multiplicação do
vetor de Attributes pela matriz de entidades do PON, resultando no vetor das
aprovações das Rules, o que será explicado abaixo.
De antemão, certamente não existe apenas uma forma de converter
Premises, Conditions e Rules em uma matriz esparsa. Apenas representando
computacionalmente o grafo de interdependências das entidades em uma aplicação
PON como uma matriz já seria, por si só, uma matriz esparsa, e assim o algoritmo
de SpMV ditaria a forma de navegar neste grafo. Entretanto, este trabalho buscou
uma forma de representação que permitisse, de fato, realizar operações
matemáticas sobre a matriz que equivaleriam as notificações, conforme a
formalização da próxima seção.
Isto tudo dito, a acima chamada matriz da operação de SpMV dos operadores
lógico-causais é aqui definida como um conjunto de matrizes, dado que uma matriz
pode ser decomposta como a multiplicação de outras matrizes. Assim, pode-se

33

definir uma matriz para Premises, em que seus elementos são definidos em termos
dos Attributes relacionados a cada Premise, bem como uma matriz para as
Conditions, definida em termos das Premises relacionadas a cada Condition. A
multiplicação dessas duas matrizes resulta em uma matriz de Rules, definida em
termos da relação entre cada Rule com cada Attribute, o que é explicado nesta
presente seção. Assim sendo, para começar tal explicação, retoma-se o exemplo
advindo da Figura 1. Tal exemplo é refeito no Código 4, que segue logo abaixo. Tal

3.3 Framework MBRIS 0.1
A fim de pôr em prova a formalização definida na seção anterior, foi
desenvolvido um framework de prova de conceito, denominado MBRIS (MatrixBased Rule Inference System) 0.13. A razão da versão dada ser 0.1 e não 1.0 como
nos demais frameworks do PON é, em primeiro lugar, para evidenciar o caráter
prototipal do framework, não sendo adequado para aplicações comerciais inclusive
e, em segundo lugar, pois existe a intenção de dar continuidade ao desenvolvimento
dele como um trabalho futuro deste TCC.
O framework foi projetado para executar tanto inteiramente em CPU, quanto
parcialmente em CPU para a parte facto-execucional do PON e em GPU para o
fluxo de notificações da parte lógico-causal do PON. Foram utilizadas as linguagens
de programação C++, para o código executado em CPU, e OpenCL, para o código
executado em GPU. Apesar de existirem hoje tecnologias de execução de código
em GPU mais avançadas do que o OpenCL, ele foi escolhido pela maior
simplicidade de uso, desempenho satisfatório e por ser amplamente suportado por
diferentes hardwares no mercado.
O framework MBRIS 0.1 é dividido em duas partes principais: o mecanismo
de inferência por notificações, implementado à luz do conceito de matriz de
ativadores exposto na seção anterior, e a interface PON, a qual permite a
construção de aplicações PON com o framework.

previamente, foi escolhido o formato CSR para a implementação do MBRIS 0.1,
dada a sua simplicidade de implementação, desempenho satisfatório e, em especial,
menor espaço necessário para representar a matriz esparsa. Tal característica é
essencial para reduzir a quantidade de transferências de dados necessárias entre
CPU e GPU para a versão do mecanismo de notificações implementada em
OpenCL, tendo em vista que tais transferências tendem a ser custosas e impactam
negativamente no desempenho da aplicação.
A classe Activator traduz, programaticamente, os conceitos de funções de
ativação e indicadores de função de ativação, expostos na subseção 3.2.2. Embora
implementar ela em C++ tenha sido relativamente simples, graças ao dinamismo da
linguagem e aos elementos da biblioteca padrão, a implementação desses conceitos
em OpenCL exigiu algumas adaptações, dada a natureza estática da linguagem e
sintaxe baseada na linguagem de programação C pura. Entre eles, uma instância
Activator em OpenCL é composta apenas por um label, o qual representa sua
função de ativação, e o coeficiente, que pode ser um valor do tipo double ou um
contador, que indica quantos ativadores diferentes estão compostos dentro do
ativador principal. A implementação da classe Activator em OpenCL se encontra no
Apêndice B deste documento.

3.3.2.4 Condition
Assim como as Premises, o equivalente a Condition em MBRIS foi
implementada como uma forma específica de criar uma instância da classe
MixedEntityMtx, em detrimento da implementação usual de frameworks PON ao
implementar a entidade Condition como uma classe específica. O equivalente a uma
Condition no MBRIS é uma MixedEntityMtx composta por uma ou mais instâncias de
MixedEntityMtx como dependências, sendo que a sua RuleMtx interna é
customizada para ser aprovada ou desaprovada conforme o tipo da Condition
(conjunção ou disjunção) e a quantidade de dependências. No entanto, tudo isso é
abstraído do programador, por meio da função BuildCondition, exemplificada no
Código 10.

52

Código 10 - Exemplo de instanciação de Conditions
auto pr1 = mbris::NOP::BuildPremise(...);
auto pr2 = mbris::NOP::BuildPremise(...);
auto pr3 = mbris::NOP::BuildPremise(...);
auto pr4 = mbris::NOP::BuildPremise(...);
// pr1 and pr2
mbris::NOP::SharedCondition cdPr1AndPr2{
mbris::NOP::BuildCondition<
mbris::NOP::EConditionType::Conjunction>(pr1, pr1)};
// pr3 or pr4
auto cdPr3OrPr4 = mbris::NOP::BuildCondition<
mbris::NOP::EConditionType::Disjunction>(pr1, pr1)};

3.3.2.5 Rule
Assim como os Attributes, uma Rule PON no MBRIS é a classe RuleMtx base
do framework. Uma Rule no MBRIS 0.1 é composta como por uma lista de
dependências, que pode ser formada por AttributeMtxs ou valores do tipo double;
uma lista de pesos, isto é, os coeficientes dos indicadores de funções de ativação
para cada dependência, os quais serão alocados na matriz durante um ciclo de
notificações; uma função de ativação e uma Action na forma de uma instância
especializada do tipo std::function, presente na biblioteca padrão do C++.
Embora seja possível instanciar uma Rule diretamente pelo construtor da
classe RuleMtx e adicionar suas dependências e pesos manualmente, tal atitude é
mais passível de erros de programação e dificulta a legibilidade do código. Portanto,
é recomendável utilizar o tipo especializado SharedRule e a função BuildRule,
fornecidos pela interface PON do framework. Tal interface possibilita ainda que uma
Condition seja adicionada como dependência da Rule, em vez de Attributes
diretamente, seguindo o modelo usual do PON e abstraindo detalhes de
implementação. Em tempo, caso não exista a necessidade de compartilhar as
Premises e/ou Conditions em outras Rules, as mesmas podem ser instanciadas
diretamente durante a construção de uma Rule, sem acarretar perda de coesão e
desacoplamento e permitindo uma programação mais alto nível. A instanciação da
regra sensorRule, presente na Figura 1, é apresentada no Código 11.

53

Código 11 - Instanciação da regra sensorRule da Figura 1 utilizando a interface PON do MBRIS
mbris::NOP::SharedAttribute atIsRead{mbris::NOP::BuildAttribute(0)};
mbris::NOP::SharedAttribute
atIsActivated{mbris::NOP::BuildAttribute(0)};
// if atIsRead == 0 and atIsActivated == 1 then ...
mbris::NOP::SharedRule sensorRule = mbris::NOP::BuildRule(
"sensorRule",
mbris::NOP::BuildCondition<
mbris::NOP::EConditionType::Conjunction>(
mbris::NOP::BuildPremise(

ACTION({

})
);

Em resumo, com essa interface PON no MBRIS, quando um Attribute tem seu
estado alterado, este irá requisitar a alocação de notificações para as Premises que
dependem dele ao Executor. Se as Premises mudarem de estado, elas farão o
mesmo para as notificações com as Conditions, que posteriormente também irão
alocar notificações para as Rules, completando o fluxo lógico-causal do PON.
3.3.3 Limitações do Framework MBRIS 0.1
Apesar de ser suficiente como prova de conceito da viabilidade de traduzir o
PON para uma operação de multiplicação de uma matriz esparsa por um vetor
denso, o Framework MBRIS 0.1 possui limitações tanto quanto ao PON em si, tanto
quanto à formalização do conceito de matriz de ativadores. Algumas podem ser
superadas em trabalhos futuros sobre o próprio framework, outras, no entanto,
exigiriam mudanças na formalização ou ainda no modelo de tradução do PON para
operações de SpMV.
Em relação ao PON, o Quadro 1 ilustra os conceitos do PON contemplados
pelo MBRIS 0.1, em comparação com alguns dos principais frameworks vigentes do
PON. Além disso, o Quadro 2 resume as propriedades elementares do PON
contempladas pelo MBRIS 0.1. Nota-se que o Framework MBRIS 0.1, embora ainda
em caráter prototipal, contempla boa parte dos conceitos e propriedades

elementares do PON, não estando muito distante dos demais frameworks PON
escritos em C++.
É pertinente ressaltar ainda que, em questão de paralelismo, mesmo que
outros frameworks PON também alcancem um certo grau de paralelismo, apenas o
MBRIS 0.1 é capaz de realizar notificações massivamente paralelas, graças ao uso
de OpenCL para executar as notificações em GPU em vez de CPU. Entretanto, o
Framework MBRIS 0.1 não implementa por completo as entidades do fluxo factoexecucional do PON, cabendo ao desenvolvedor de uma aplicação no framework
decidir como estruturar a Action de uma Rule.

Em relação à formalização da matriz de ativadores, o MBRIS 0.1 não
implementa nenhum mecanismo automático para combinação ou compartilhamento
de linhas, cabendo ao programador de uma aplicação no framework estruturar as
instâncias de Rules de forma a não gerar redundâncias de notificações e/ou mais
notificações do que o necessário. Tal mecanismo, no entanto, é viável de ser
implementado no futuro.
Por fim, o MBRIS 0.1 carece de maior flexibilidade de programação em
relação aos tipos de dados dos Attributes. Isto porque, conforme evidenciado pelo
diagrama de classes e códigos mostrados anteriormente, somente o tipo de dados
double é permitido, enquanto o Framework PON C++ 4.0, por exemplo, permite
Attributes de qualquer tipo de dados do C++, seja ele um tipo primitivo (e.g., int,
double, char, bool etc.) ou um tipo customizado (NEVES, 2021). O MBRIS 0.1 foi
implementado com essa limitação pela dificuldade de realizar operações aritméticas
com tipos de dados não-numéricos em OpenCL, acarretando a necessidade de
definir, por parte do programador de uma aplicação em MBRIS, exatamente como
realizar as operações aritméticas para cada tipo de dados não-numérico utilizado na
aplicação em código OpenCL. A escolha do tipo double então, em vez do tipo int ou
alguma de suas variações, se deu para ao menos amenizar o problema, visto que o
tipo double suporta tanto operações de ponto flutuante com maior precisão, como
operações com números inteiros.

4 TESTES E RESULTADOS
Esta seção apresenta os testes do framework proposto, Framework MBRIS
0.1, focando em comprovar sua funcionalidade e em analisar o desempenho do
framework em diferentes cenários. O objetivo é validar a formalização da matriz de
ativadores e o modelo de execução do fluxo de notificações do PON por meio de
operações de SpMV como uma forma possível de implementar o mecanismo de
notificações do PON.
Ainda, o desempenho do Framework MBRIS 0.1 foi comparado com o
desempenho do Framework PON C++ 4.0, a fim de compreender como novo modelo
proposto para o mecanismo de notificações do PON e sua primeira implementação
se comparam ao modelo e implementação vigentes no tocante ao estado da técnica.
Nesse sentido, foi desenvolvida uma aplicação de testes que simula a leitura
de sensores de alarme, clássica da literatura do PON, sendo que ela foi explorada
em diferentes cenários de execução. A seção 4.1 trata do desenvolvimento da
aplicação e testes realizados, e a seção 4.2 traz as considerações gerais sobre os
resultados obtidos.
4.1 Aplicação de sensores (NOPSensor)
A aplicação de sensores, denominada NOPSensor, consiste em simular a
leitura de diversos sensores de alarme por meio do fluxo de notificações do PON.
Ela foi desenvolvida com base no FBE e Rule da Figura 1 e Código 4, sendo uma

4.2 Considerações sobre os resultados
A partir dos resultados obtidos na seção anterior, o Framework MBRIS 0.1 se
mostrou viável para o desenvolvimento de aplicações PON, mesmo se encontrando
ainda em um estado prototipal. Sua interface de programação PON o aproxima
bastante do Framework PON C++ 4.0, atualmente o estado da técnica do PON,
facilitando a tradução de aplicações desenvolvidas Framework PON C++ 4.0 para o
MBRIS. Além disso, inspirado na matriz de ativadores, o MBRIS permite uma
representação simplificada das entidades lógico-causais do PON, combinando
previamente Rules, Conditions e Premises em cenários em que não há necessidade
de compartilhar entidades, eliminando notificações desnecessárias em troca de
maior desempenho.
Em relação ao desempenho, o Framework MBRIS 0.1 obteve um
desempenho substancialmente inferior ao Framework PON C++ 4.0 para a aplicação
NOPSensor. Mesmo com os esforços para otimizar a aplicação para o MBRIS e com
a inovação de executar notificações por meio operações de SpMV, fazendo uso do
OpenCL para que as notificações fossem executadas de maneira altamente paralela
em GPU, o overhead causado pela implementação do MBRIS, muito dependente de
locks entre as diferentes threads durante a alocação das entidades nas matrizes, e
pela transferência de dados entre CPU e GPU, fez com que o tempo de CPU da
aplicação NOPSensor em MBRIS com OpenCL fosse sete mil vezes maior do que a
versão monoprocessada no Framework PON C++ 4.0 quando apenas uma Rule foi
aprovada, e vinte vezes maior quando todas as cem mil Rules foram aprovadas,
conforme pode ser verificado ao comparar os dados entre das Tabelas 3 e 4.
Em termos do processamento das notificações em si, apenas considerando
as variações do MBRIS, o tempo de execução do compute kernel em GPU pelo
MBRIS com OpenCL aumentou consideravelmente menos do que o tempo de CPU
ao aumentar a quantidade de Rules aprovadas, evidenciando a superioridade do
OpenCL e do hardware de GPUs quando se trata de paralelismo. Nesse sentido,
visando melhorar o desempenho do Framework MBRIS 0.1, torna-se necessário,
num primeiro momento, otimizar o código do framework que roda em CPU,
reduzindo o travamento entre threads. Além disso, na implementação atual do

69

framework, a lógica de ativação dos indicadores de função de ativação é executada
apenas em CPU, sendo apenas o cálculo dos coeficientes realizado em GPU por
meio de operações de SpMV. Transferir essa lógica para o código em OpenCL
poderia reduzir o tempo de CPU do framework e, mesmo que não fosse suficiente
para tornar o MBRIS mais rápido do que o Framework PON C++ 4.0, ao menos
tornaria seu desempenho mais próximo.
No entanto, é pertinente ressaltar que a aplicação NOPSensor é
extremamente simples e que mesmo a sua versão multithreaded no Framework
PON C++ 4.0 não apresenta ganhos significativos de desempenho comparada com
a versão single-thread. Como o escopo deste trabalho se reduziu apenas a realizar
uma prova de conceito, ela foi suficiente para compreender melhor o funcionamento
do MBRIS e comprovar a viabilidade do conceito de matriz de ativadores para
implementar o mecanismo de notificações do PON. Nesse sentido, um trabalho
futuro seria o desenvolvimento de outras aplicações em MBRIS para explorar
diferentes cenários, inclusive os que exigem paralelismo, visando compreender
como o MBRIS se comporta em aplicações mais complexas e melhor identificar se
ele poderia ser viável para uso em aplicações reais, sejam elas de caráter
acadêmico e/ou industrial.

5 CONCLUSÃO
As próximas seções trazem as conclusões gerais deste trabalho à luz dos
objetivos expostos nas Seções 1.3.1 e 1.3.2, bem como possíveis trabalhos futuros.
A Seção 5.1 trata dos resultados gerais obtidos com o desenvolvimento do trabalho.
A Seção 5.2 retoma os objetivos deste trabalho para analisar se foram atingidos. As
considerações finais são elaboradas na Seção 5.3, em especial no que tange à
inovação aqui proposta e ao histórico dos trabalhos sobre o Paradigma Orientado a
Notificações. Por fim, a Seção 5.4 apresenta possíveis trabalhos futuros, visando
tanto explorar a inovação deste trabalho em diferentes contextos, quanto dar
continuidade ao desenvolvimento do MBRIS.
5.1 Resultados em geral
O presente trabalho se propôs a formalizar e implementar um novo
mecanismo de execução do fluxo lógico-causal de notificações do Paradigma
Orientado a Notificações (PON). Tal mecanismo animaria as notificações de forma
extraordinária, por meio de operações de multiplicação de matrizes esparsas por um
vetor. Esse novo método para executar as notificações possibilitaria a execução
altamente paralela de notificações em hardwares aceleradores, como placas de
vídeo.
O primeiro passo para o desenvolvimento do trabalho foi desenvolver tanto
proposição quanto a formalização do mecanismo de inferência do PON baseado em
multiplicação de matrizes esparsas. Eis que a proposição e formalização de tal
solução tem como núcleo a chamada “matriz de ativadores”. Tal “matriz de
ativadores” tem como objetivo poder traduzir expressões lógico-causais do tipo seentão, as quais servem como base para o modelo do PON, em operações de
multiplicação de matrizes por um vetor. O cerne da formalização se encontra no
conceito de indicadores de função de ativação, um tipo especial de coeficiente com
propriedades lineares, mas que aplica uma função sobre si mesmo para dar o
resultado de uma expressão lógica (i.e., verdadeiro ou falso).
Com base na proposição e formalização da solução pretendida, foi
desenvolvido um novo framework PON em C++ que implementa o conceito da matriz
de ativadores para executar o fluxo lógico-causal de notificações do PON. Tal
framework foi denominado Framework MBRIS 0.1 e, mesmo que de caráter

71

prototipal, permitiu demonstrar tecnicamente a viabilidade desse novo conceito.
Ainda, visando alcançar a execução altamente paralela de notificações almejada, o
framework utiliza, além das técnicas de SpMV da solução proposta, também a
ferramenta OpenCL, a qual permite execução de compute kernels em GPUs de
maneira simplificada.
Para pôr em prova a implementação da solução, a fim de entender como ela
se comporta em aplicações reais e identificar seus pontos positivos e negativos, foi
desenvolvida uma aplicação de simulação de leitura de sensores com o Framework
MBRIS 0.1 em três diferentes versões. Cada versão teve seu desempenho
comparado com a mesma aplicação desenvolvida com o Framework PON C++ 4.0.
Muito embora o resultado dos experimentos não tenha sido favorável para o MBRIS,
que obteve um tempo de CPU sete mil vezes maior do que o Framework PON C++
4.0, quando apenas uma Rule foi aprovada, e vinte vezes maior quando todas as
cem mil Rules foram aprovadas, o experimento pode demonstrar o funcionamento
do Framework MBRIS 0.1, abrindo portas para trabalhos futuros ademais.
5.2 Resultados vis-à-vis objetivos
Ao longo de todo o desenvolvimento deste trabalho, foram considerados os
objetivos específicos definidos na Seção 1.3.2, visando alcançar o objetivo geral
definido na Seção 1.3.1. Diversas ações foram tomadas para atingir cada um dos
objetivos, detalhadas a seguir.
O primeiro objetivo foi propor uma forma de traduzir as expressões lógicas do
Paradigma Orientado a Notificações para operações de multiplicação de matrizes
esparsas por um vetor denso. A tradução proposta na Seção 3.1 buscou respeitar os
princípios primordiais de não-redundância temporal e estrutural do PON, ao mesmo
tempo em que vislumbrou uma forma inovadora de executar o fluxo lógico-causal de
notificações do PON, por meio de um novo mecanismo de execução das
notificações.
Em seguida, a Seção 3.2 descreveu a formalização teórica e matemática para
este novo mecanismo inovador. Ao fazer uso de um coeficiente especial, chamado
de indicador de função de ativação, foi possível traduzir as expressões lógicas do
PON para um cálculo aritmético de matrizes, denominadas matrizes de ativadores,
sendo o conjunto destas matrizes uma representação aritmética da dependência

72

entre as diferentes entidades lógico-causais do PON. Tal formalização é coerente
com o segundo objetivo do trabalho.
O terceiro objetivo foi contemplado com o projeto de desenvolvimento de um
novo framework PON. Batizado de Framework MBRIS 0.1 e inspirado na
formalização e no conceito da matriz de ativadores, tal framework implementou um
mecanismo de execução do fluxo lógico-causal de notificações por meio de
operações de Sparse Matrix-Vector Multiplication. Nesse sentido, visando respeitar
os princípios do PON, o uso de matrizes esparsas e de algoritmos de SpMV
garantiram que não houvesse processamento lógico-causal redundante e que
apenas as notificações necessárias fossem executadas. Ainda, para alcançar um
alto grau de paralelismo, o Framework MBRIS 0.1 foi desenvolvido utilizando a
tecnologia OpenCL, a qual permite execução altamente paralela de código em
hardwares aceleradores, como placas de vídeo.
Por fim, para contemplar o último objetivo do trabalho, foi implementada a
aplicação NOPSensor, clássica da literatura do PON, utilizando o framework
desenvolvido. O desempenho da aplicação foi medido em diversos cenários e então
comparado com a implementação da mesma aplicação no Framework PON C++ 4.0,
atual estado da técnica do PON a nível de frameworks, desenvolvida por Neves
(2021). Embora seja simples, tal experimento demonstrou tecnicamente a viabilidade
do mecanismo inovador proposto neste trabalho para executar o fluxo lógico-causal
de notificações do PON.
Portanto, com todas as ações tomadas acima, é possível verificar que os
objetivos deste trabalho foram atingidos com êxito, contribuindo para o avanço da
pesquisa acerca do Paradigma Orientado a Notificações, em especial, no que tange
ao paralelismo de notificações, formalização teórica da dependência entre as
entidades do paradigma e execução de código PON em hardwares distintos.
5.3 Considerações finais
O mecanismo de execução do fluxo lógico-causal de notificações do PON
proposto, formalizado e implementado no Framework MBRIS 0.1 apresenta uma
inovação na forma de implementar e executar o PON em software. Ainda que os
resultados dos experimentos não tenham sido promissores em termos de
desempenho do framework em um primeiro momento, é pertinente lembrar que

73

todas as inovações do paradigma demandaram algumas iterações até que fossem
alcançados os resultados almejados.
Exemplos de tais iterações refinadoras são as que seguem: do Framework
CON/PON C++ Prototipal (SIMÃO, 2001; SIMÃO; STADZISZ, 2008) ao Framework
PON C++ 4.0 (NEVES, 2021), das primeiras tentativas de distribuição no Framework
PON C++ 2.0 com PON-IP e paralelismo no Framework PON C++ 3.0 (BELMONTE
et al., 2012; SCHÜTZ, 2019) até os recentes Framework PON Elixir/Erlang
(NEGRINI et al., 2019) e Framework PON C++ 4.0 IOT (FIGUEIREDO, 2022), e da
Tecnologia LingPON 1.0 até a Tecnologia LingPON 3.0 (CHIERICI; SKORA; SIMÃO,
2022). Assim, não poderia ser diferente com o MBRIS, sendo que os trabalhos
futuros descritos abaixo podem guiar as futuras iterações do framework, visando
sempre avançar a pesquisa do PON. Este trabalho, portanto, cumpriu ao que se
propôs e servirá de base para que inovações ainda maiores do as aqui descritas
sejam desenvolvidas no futuro.
5.4 Trabalhos futuros
O presente trabalho abre caminho para trabalhos futuros, desde melhorias no
próprio Framework MBRIS, a fim de torná-lo industrialmente viável, até novas
iniciativas para a execução de aplicações PON em placas de vídeo ou hardwares
aceleradores distintos.
Em relação ao MBRIS, é necessário ainda o desenvolvimento de novas
aplicações mais complexas e em cenários mais favoráveis ao paralelismo, para
compreender melhor suas capacidades e identificar se ele poderia ser viável para
uso em aplicações reais (acadêmicas ou industriais) no futuro. Podem ainda ser
explorados diferentes formatos de armazenamento para matrizes esparsas, levando
a diferentes algoritmos de SpMV, a fim de identificar qual deles é o mais adequado
para o PON.
A implementação do framework também pode ser aprimorada, tanto o código
em C++, quanto o código em OpenCL. A parte em C++ poderia ser refatorada para
diminuir os travamentos entre threads e reestruturar algumas funções internas do
framework. Além disso, a lógica de ativação dos indicadores de função de ativação
pode ser transferida do C++ para o OpenCL, e a implementação da matriz de
ativadores em OpenCL pode ser melhorada e possivelmente otimizada para algum
hardware em específico. O próprio OpenCL pode ser substituído no MBRIS por outra

74

tecnologia/ferramenta de programação paralela mais moderna, a fim de alcançar um
desempenho superior. Por fim, é preciso tornar o framework mais flexível em termos
dos tipos de dados aceitos para os Attributes, para expandir a gama de aplicações
viáveis de serem desenvolvidas com o framework.
Em relação ao modelo de execução do PON através de operações de SpMV,
um modelo diferente do proposto neste projeto pode ser desenvolvido e comparado
com a matriz de ativadores, a fim de explorar outras alternativas para a execução de
programas PON em hardwares como o de GPUs. Inclusive, outros compute kernels,
inspirados ou não no SpMV, podem ser utilizados para um possível novo modelo de
execução do PON.
Por fim, muito embora este trabalho tenha explorado o conceito de matriz de
ativadores e o Framework MBRIS 0.1 sob a ótica do PON, tanto a formalização,
quanto o framework são mais flexíveis do que o PON propriamente dito e
possibilitam modelos de programação diferentes do modelo do PON. A matriz de
ativadores é nada mais do que uma ferramenta para converter qualquer expressão
lógica em um cálculo aritmético de multiplicação de matrizes por um vetor. Assim,
existe a possibilidade de se desenvolver diversos trabalhos explorando o conceito da
matriz de ativadores sobre outras óticas, desde a computação teórica até a de
outros modelos de programação.
Em suma, os trabalhos futuros aqui apresentados evidenciariam o potencial
do framework, do conceito de matriz de ativadores e da ideia de executar PON em
hardwares distintos, dando continuidade ao desenvolvimento do paradigma e da
programação paralela.

#define MAX_MAP_ENTRIES_PER_ACTIV 10
#pragma OPENCL EXTENSION cl_khr_fp64 : enable
typedef union
{
double d;
int activ_map_counter;
} cl_coefficient_t;
typedef enum
{
DOUBLE
= 0,
ACTIV_MAP = 1
} COEF_TYPE;
typedef struct
{
int label;
double coef;
} cl_simple_activator_t;
typedef struct
{
int label;
COEF_TYPE coef_type;
cl_coefficient_t coef;
} cl_activator_t;
typedef enum
{
EL_DOUBLE = 0,
EL_ACTIV = 1
} ELEM_TYPE;
typedef struct
{
ELEM_TYPE elem_type;
union {
double d;
cl_activator_t activ;
} data;
} cl_matrix_element_t;
__kernel void spmv_csr(
__global const cl_matrix_element_t* restrict data,
__global const double* restrict vec,
__global const ulong* restrict col_idxs,
__global const ulong* restrict row_ptrs,
__global cl_matrix_element_t* restrict out,
__global cl_simple_activator_t* restrict activ_map,
const ulong dim
)
{
const ulong row = get_global_id(0);
if(row >= dim) return;
cl_matrix_element_t res;
res.elem_type = EL_DOUBLE;
res.data.d = 0.0;
const ulong start = row_ptrs[row];
const ulong end = row_ptrs[row + 1];
const ulong activ_map_start = row * MAX_MAP_ENTRIES_PER_ACTIV;
int map_counter = -1;
for(int i = start; i < end; ++i)
{
const ulong col = col_idxs[i];

89

const double x = vec[col];
cl_matrix_element_t elem = data[i];
if(EL_DOUBLE == elem.elem_type)
{
if(EL_DOUBLE == res.elem_type)
{
res.data.d += elem.data.d * x;
}
else
{
if(DOUBLE == res.data.activ.coef_type)
{
res.data.activ.coef.d += elem.data.d * x;
}
else
{
bool found = false;
for(int j = 0; j < res.data.activ.coef.activ_map_counter; ++j)
{
cl_simple_activator_t map_elem = activ_map[activ_map_start + j];
if(-1 == map_elem.label)
{
found = true;
activ_map[activ_map_start + j].coef += elem.data.d * x;
break;
}
}
if(!found)
{
map_counter++;
cl_simple_activator_t new_activ;
new_activ.label = -1;
new_activ.coef = elem.data.d * x;
activ_map[activ_map_start + map_counter] = new_activ;
res.data.activ.coef.activ_map_counter = map_counter + 1;
}
}
}
}
else
{
if(DOUBLE == elem.data.activ.coef_type)
{
if(EL_DOUBLE == res.elem_type)
{
elem.data.activ.coef.d *= x;
elem.data.activ.coef.d += res.data.d;
res.elem_type = EL_ACTIV;
res.data.activ = elem.data.activ;
}
else
{
if(DOUBLE == res.data.activ.coef_type)
{
if(elem.data.activ.label == res.data.activ.label)
{
res.data.activ.coef.d += elem.data.activ.coef.d * x;
}
else
{
map_counter++;
cl_simple_activator_t new_activ;
new_activ.label = res.data.activ.label;
new_activ.coef = res.data.activ.coef.d;
activ_map[activ_map_start + map_counter] = new_activ;

90

map_counter++;
new_activ.label = elem.data.activ.label;
new_activ.coef = elem.data.activ.coef.d * x;
activ_map[activ_map_start + map_counter] = new_activ;
res.data.activ.coef_type = ACTIV_MAP;
res.data.activ.coef.activ_map_counter = map_counter + 1;
}
}
else
{
bool found = false;
for(int j = 0; j <= map_counter; ++j)
{
cl_simple_activator_t map_elem = activ_map[activ_map_start +
j];
if(elem.data.activ.label == map_elem.label)
{
found = true;
activ_map[activ_map_start + j].coef +=
elem.data.activ.coef.d * x;
break;
}
}
if(!found)
{
map_counter++;
cl_simple_activator_t new_activ;
new_activ.label = elem.data.activ.label;
new_activ.coef = elem.data.activ.coef.d * x;
activ_map[activ_map_start + map_counter] = new_activ;
res.data.activ.coef.activ_map_counter = map_counter + 1;
}
}
}
}
else
{
// Not supported
}
}
out[row] = res;
}
